# Gap Analysis

Gaps found by comparing `RD.md`/`ARCHITECTURE.md`/`DESIGN.md`/`RULES.md`/`TASKS.md`/`MEMORY.md` against each other and against the actual repository state (migrations, models, routes, tests) as of this audit.

| Area | Current State | Gap | Impact | Recommendation | Phase |
| --- | --- | --- | --- | --- | --- |
| Documentation | `TASKS.md` 0.4 lists "Apply the schema to the development database" as not started | The migration table shows all 21 migrations already ran (`php artisan migrate:status`) against the configured database | Low — a contributor following `TASKS.md` literally would re-run a migration that's already applied, which is harmless but wastes time and casts doubt on the rest of the checklist's accuracy | Check off that line and the "drop `pm_schema_check`" line once confirmed dropped; keep `TASKS.md` synced with actual state going forward | Immediate, documentation-only |
| Authorization | `TeamRole` and `ProjectMemberRole` both exist and are implemented; `RD.md` §1 names 5 actors | No document maps RD.md's actors (owner, project manager, team lead, contributor, client) onto the two enums' 12 combined values | Medium — without this mapping, `ProjectPolicy`/`TaskPolicy` (TASKS 1.2/1.5) will be written ad hoc per-developer and likely diverge from what RD.md promised | Needs Decision — see `open-decisions.md` OD-1 | Before Phase 1 policies are written |
| Project visibility | FR-1.6 says a user sees only projects "where the user is a member unless the team role grants wider visibility" | Which `TeamRole` value(s) grant that wider visibility is unspecified; no visibility enum exists on `projects` | Medium — `ProjectPolicy` and the project list query can't be written correctly without this | Needs Decision — see `open-decisions.md` OD-4 | Before Phase 1 |
| Notifications | `TASKS.md` Phase 7 has "Notification preferences per user" and "Minutes published notification to attendees" as line items | No FR in `RD.md` defines notification triggers, channels, or a `notifications`/preferences table in `DESIGN.md`'s table inventory | Medium — Phase 4 and Phase 7 tasks reference a system that doesn't exist yet at the data-model level | Add a `NOTIFY-*` FR set to `RD.md` and a `notifications`/`notification_preferences` table to `DESIGN.md` before Phase 4 starts (meeting minutes notification is the earliest consumer) | Before Phase 4 |
| Search | Not mentioned anywhere in `RD.md`, `ARCHITECTURE.md`, or `DESIGN.md` | A project-management tool with projects, tasks, comments, and users will need search well before "Future"; MySQL `LIKE`/fulltext is likely sufficient at MVP scale (NFR-6's stated ceiling is 50 users) | Low now, growing over time | Record as a Future-phase FR (`SEARCH-001` in `requirement-traceability.md`); no infrastructure decision needed yet — plain MySQL queries are adequate until usage data says otherwise | Future |
| API strategy | `RD.md` §4 explicitly scopes the current phase to "the data layer," deferring "HTTP controllers and Inertia pages"; no REST API is mentioned for anything except inbound Git webhooks | The original stack description mentions "REST/API where appropriate" but `RD.md` never says what that API is for (mobile app? third-party integrations? none?) | Low today (nothing depends on it yet), but it changes the shape of controllers if decided later (Resource classes, versioning) | Needs Decision — see `open-decisions.md` OD-3 | Needs Decision, revisit at start of Phase 1 |
| File attachments | `attachments` table exists (polymorphic file metadata); FR-9.3 is a single sentence | No size limit, MIME allowlist, storage disk (local vs S3), or signed-URL policy is documented anywhere, and `FILESYSTEM_DISK=local` in `.env` is not asserted as a deliberate production choice | Medium — Phase 7's `AttachmentController` (TASKS.md) can't be built safely without this; unvalidated uploads are an OWASP-relevant risk (see Security Review below) | Needs Decision — see `open-decisions.md` OD-2 | Before Phase 7 |
| Soft-delete coverage | `DESIGN.md` documents soft deletes for `projects`, `project_modules`, `project_members`, `tasks`, `git_repositories` (driven by the unique-key discussion in §3.4) | No single table enumerates every model and states soft-delete yes/no; `comments`, `attachments`, `meetings`, `todo_lists`/`todo_items`, `milestones`, `sprints` were not confirmed either way in this pass | Low-medium — inconsistent soft-delete coverage produces surprising cascade/restore behavior later | Add a one-page soft-delete table to `DESIGN.md` (model → soft-deleted? → cascade behavior) before Phase 1 controllers start deleting things | Before Phase 1 |
| Invariant enforcement | `DESIGN.md` §5 and `MEMORY.md` both name three unenforced invariants: `todo_lists.type`-to-context rules, a task's module belonging to its project, and `task_dependencies` cycles | `TASKS.md` 0.4 lists "Model observers enforcing the invariants" as not started | High once Phase 1/3 controllers exist — without these, a form bug can create silently-corrupt data (a task dependency cycle, a checklist item with no task) with no test catching it until it's in production | Build the three observers before or alongside the first controller that writes each affected table (task creation, dependency creation, todo-list creation) | Phase 1 (task/module), Phase 3 (todo lists) |
| Cross-team test coverage | `RULES.md` §9 mandates an unauthenticated, unauthorized, and cross-team test per endpoint; 3 feature tests currently exercise this pattern (`ProjectMemberTest`, `ResourceAllocationTest`, `TaskTest`) | No controllers exist yet to have endpoints, so this is not violated today, but there is no tracking mechanism to confirm the rule is followed once Phase 1 controllers land | Medium, self-inflicted risk if unaddressed | Add "cross-team case present" as a required checklist item in PR review, not a new tool — `RULES.md` §11 (Definition of Done) is the natural home | Ongoing from Phase 1 |
| Documentation structure | Six flat top-level `.md` files (`RD.md`, `ARCHITECTURE.md`, `DESIGN.md`, `RULES.md`, `TASKS.md`, `MEMORY.md`) | No `README.md` exists, so a new contributor has no single entry point naming what each file is for | Low | Add a short `README.md` that links the six documents and states the one-line purpose of each (see Final Report §16) | Immediate, documentation-only |
| Onboarding vs correctness docs | `MEMORY.md` mixes durable environment facts (MySQL socket-only, missing `pdo_sqlite`) with one-time historical narrative ("2026-09-20 — Database redesign") | Not a defect — `MEMORY.md`'s own header says "append, do not rewrite," so this is by design — but the file will keep growing and the environment facts at the top are the ones a new contributor needs first | None currently | No action needed; flagging only so a future reorganization isn't mistaken for fixing a "gap" | N/A |
| Timezone handling | NFR-8 requires UTC storage with the work schedule carrying its own timezone | Whether `user_work_schedules` actually has a `timezone` column was not confirmed in this pass (not read in the migration file) | Unknown — needs a direct check | Verify `user_work_schedules` migration has a `timezone` column before Phase 6 starts; if absent, add it there rather than retrofitting later | Verify before Phase 6 |
| Rate limiting | No mention in `RD.md`, `RULES.md`, or `ARCHITECTURE.md` | Login, registration, invitation acceptance, and (later) Git webhook endpoints are natural abuse targets with no stated throttle policy | Medium | Add explicit throttle requirements to `RULES.md` §1 (Non-Negotiables) covering auth routes now and webhook routes when Phase 5 lands | MVP for auth, Phase 5 for webhooks |
| Client project membership | ADR-008 (this audit) states a Client never holds a `TeamRole`; `ProjectMemberController::store()` (Phase 1.4, built) only allows adding users already present in `team_members` | A genuinely external client — someone with zero presence on the team — cannot be added as a project member today, because `EnsureTeamMembership` requires `belongsToTeam()` for every route under `{current_team}`, and `belongsToTeam()` requires a `team_members` row, which requires a `TeamRole` | Medium — blocks a literal reading of RD.md's "Client" actor for anyone who isn't already on the team | Needs Decision: either (a) add a minimal `TeamRole` case with zero permissions purely to satisfy `belongsToTeam()`, revising ADR-008, or (b) extend `EnsureTeamMembership` to also accept a user with an active `ProjectMemberRole` on a project within that team, even with no `TeamRole` row at all. Not blocking today — every team member can currently be added to a project with any `ProjectMemberRole` including Client | Before a genuine external-client invitation flow is built (not currently scheduled in `TASKS.md`) |
