## Phase 2 — Progress Monitoring

- [x] `CalculateProjectProgress` action rolling task completion up to module, milestone and project (FR-4.1). Module progress counts only tasks directly assigned to that module — it does not recurse into child modules; a nested module's tasks do not count toward its parent's percentage. Progress = completed / (total − cancelled), rounded; a task set with 0 relevant tasks is 0%, not undefined.
- [x] `SnapshotProjectProgress` scheduled job (`oms:snapshot-project-progress`, daily via `routes/console.php`) writing `project_progress_snapshots` nightly (FR-4.2) — also the single writer for `projects.progress_percentage`, `projects.health`, `project_modules.progress_percentage` and `milestones.progress_percentage` (see `ARCHITECTURE.md`'s Derived Values table). Snapshot writes use `updateOrCreate` on `(project_id, sprint_id, snapshot_on)` so re-running the same day updates rather than duplicates. Only non-archived, non-terminal projects (`Project::open()`) are processed.
- [x] `DetermineProjectHealth` rule set driving `projects.health` from schedule and hours variance — takes the worse of two independent signals: schedule position (actual progress vs. where a linear schedule expects it to be, given `start_date`/`end_date`) and hours variance (logged hours vs. estimate, only while work is unfinished). A project with no `end_date` is always `on_track` — there's nothing to measure against. This overwrites any manual edit to `health` on the next nightly run; there is no override flag.
- [x] Project dashboard: completion, burndown from snapshots, overdue and blocked counts (FR-4.3) — built into the existing Overview tab rather than a separate page/tab, since it's the same project-summary surface. Burndown is a hand-rolled inline-SVG chart (no charting library added — `CLAUDE.md` requires approval for new dependencies), using this app's own `--chart-1..5` design tokens rather than inventing new colors, with a working hover crosshair + tooltip. Overdue/blocked counts are live (`CalculateProjectProgress` called fresh on every page load), not read from the last snapshot — the snapshot history only feeds the burndown line.
- [x] Portfolio dashboard across all team projects — rebuilt the existing (placeholder) `DashboardController`/`dashboard.tsx` rather than adding a new page/route, since that's already the team-level landing page. Reuses the exact visibility rule from `ProjectPolicy`/`ProjectController::index()` (team Owner/Admin see every project, everyone else only projects they're an active member of) — duplicated inline rather than extracted to a shared helper, since it's a one-line check (`$role->isAtLeast(TeamRole::Admin)`). Overdue/blocked counts are a single aggregate query each across the visible project set, not per-project queries.
- [x] `RecordActivity` action plus model observers populating `activities` (FR-4.4). Observers (`App\Observers\OMS\*`, registered in `AppServiceProvider::boot()`) cover only the unambiguous `created`/`deleted` lifecycle events on `Project`, `ProjectModule`, `ProjectMember`, `Task`, `Milestone` and `Sprint` — a generic `updated()` hook can't produce an accurate human description from a dirty-attribute diff alone. Nuanced events with real before/after semantics are logged by a direct `RecordActivity` call from the action or controller that already knows the story: `ChangeTaskStatus` (`task.status_changed`), `AssignTask` (`task.assigned` / `task.unassigned`), `AddTaskDependency` and `TaskDependencyController::destroy` (`dependency.added` / `dependency.removed`), `ProjectController::archive` (`project.archived`).
- [x] Activity feed component with project and user filters (`resources/js/components/projects/activity-feed.tsx`), wired into the project workspace's Activity tab. Scoped to the last 50 activities for the project (not paginated — same reasoning as the task list view, TASKS.md 1.5). Each mutating action's tab (Board, Modules, Members, Milestones, Sprints) now includes `'activities'` in its partial `router.reload()` so the feed stays live without a full page reload; this was caught only by driving the feature in a real browser, not by the PHP test suite.
- [x] Cycle-time and lead-time report from `task_status_histories` (`CalculateCycleTimeReport`, surfaced as a "Cycle time" card on the Overview tab, next to Burndown). Lead time is creation → completion; cycle time is first "in progress" → completion; both come from `tasks.created_at`/`started_at`/`completed_at`, which are themselves stamped exactly when the corresponding `task_status_histories` row is written — so they're accurate for the common path but, like the rest of the app, don't distinguish a re-opened-then-redone task from a first-time one (`started_at`/`completed_at` only ever record the *first* time each was reached). The report also breaks down average minutes spent per status (a bottleneck view), which needed `task_status_histories.duration_minutes` — previously declared in the schema but never populated — to actually be written by `ChangeTaskStatus` on every transition.
- [x] Reconciliation command for `logged_hours` and the progress percentages (`oms:reconcile`, scheduled nightly at 00:00, ahead of `oms:snapshot-project-progress` at 00:15 so the day's snapshot reads corrected values). `ReconcileTaskLoggedHours` is the "one writer" DESIGN.md 299 calls for — it recomputes `tasks.logged_hours` from `time_logs` (excluding rejected/cancelled entries) for every task; today that's always 0, since Phase 6's `TimeLogController` doesn't exist yet to write any `time_logs` rows, but the command is correct and ready for when it does. The progress/health half reuses `CalculateProjectProgress`/`DetermineProjectHealth` exactly like the snapshot job, but covers every project including archived ones (the snapshot job deliberately skips those) and never writes a `project_progress_snapshots` row — it repairs live columns, it doesn't record history.

## Phase 3 — To-Do Lists

- [x] `OMS\TodoListController` and `OMS\TodoItemController` (FR-5.1 – FR-5.5) — scoped to personal and daily lists (`TodoListType::Custom`/`Daily`) for this step; `task_checklist`, `meeting_actions` and `generated` are system-managed types, deliberately rejected by `SaveTodoListRequest` (a user can't hand-create one through this general form), and get their own authorization/UI in later steps (task checklists genuinely need the task detail page; meeting actions are blocked on Phase 4). `TodoListPolicy` is ownership-only (`owner_id === user->id`) — personal to-dos are private, with no team-admin override the way projects have one. Reachable at `{current_team}/todo-lists`, a new top-level "My To-Dos" sidebar link, single-page/modal UX (ADR-013). `ToggleTodoItem` implements FR-5.4: completing an item linked to a task closes that task via `ChangeTaskStatus`; un-completing an item never reopens its task (the requirement only implies one direction, and reopening a task someone else has since moved forward on would be surprising).
- [x] `GenerateDailyTodoList` action building a dated list from open assignments due soon (FR-5.6). A snapshot, not a live sync: it's idempotent per (user, team, date) — calling it again the same day returns the existing list unchanged rather than re-diffing it against tasks that have since changed status or due date, so a task someone completed still shows on that day's generated list (it isn't retroactively pruned). "Due soon" is due within 7 days, or no due date at all; `Done`/`Cancelled` tasks and assignments the user has been unassigned from are excluded, reusing the existing `TaskAssignment::active()` scope rather than re-deriving that rule. `TodoListType::Generated` is what makes the origin distinguishable from a hand-written list per FR-5.6's own wording — surfaced with a "Generated" badge on the My To-Dos page, generated automatically the moment that page is visited (same lazy-on-view pattern as the task checklist).
- [x] `PromoteTodoItemToTask` action, and the reverse for task checklists. Scoping decision: "the reverse for task checklists" is read as *which project a promoted item lands in and whether it gets a parent*, not a second action — one action handles both directions. A personal/daily/generated item has no project of its own, so the user picks one and the new task is standalone; a task-checklist item's project is already implied by the task the checklist belongs to, so no picker is shown and the new task becomes a **subtask** of that task (`parent_id` set) — a checklist line substantial enough to need its own tracking, rather than a personal item graduating into project work. `task_type_id` is always asked for (the one field `tasks` has no default for). The item's `assigned_to` carries over to the new task's assignment only when that user is an active member of the target project, so promotion can never silently create an invalid assignment. Reachable via `POST .../todo-lists/{todo_list}/items/{item}/promote`, wired into both `TodoListCard` (My To-Dos / My Day) and `TaskChecklist` (task detail page) through the same `PromoteTodoItemModal`, which shows or hides the project picker based on whether `projects` was passed in. A promoted item's row now links to its task (`item.task` in the payload) instead of showing the promote button again.
- [x] "My day" page combining personal items, task checklists and meeting actions (`{current_team}/my-day`, new sidebar link). Meeting actions are genuinely blocked, not deferred by choice — same reasoning as the task detail page's comments/attachments (Phase 1.5): Phase 4 (Meetings) has no controller yet, so there's a placeholder card rather than a query against nothing. "Task checklists" surfaces as every open `task_checklist`-type item assigned to the user across every project on the team (not just one task's checklist), reusing the same toggle route as everywhere else. Reuses `TodoListCard` verbatim for the personal/daily/generated section rather than a read-only summary, so a list can be fully managed from either My Day or My To-Dos without a mode difference between the two pages.
- [x] Task checklist component on the task detail page (`resources/js/components/projects/task-checklist.tsx`). `GetOrCreateTaskChecklist` lazily creates the task's `type=task_checklist` `TodoList` the first time its detail page is visited (idempotent — a second visit reuses the same row) rather than at task creation, so a task nobody ever checklists never gets an empty list row. Reuses the same `TodoItemController`/`TodoItemFormModal` the personal-lists step already built — no new routes needed, since an item only cares which `TodoList` it belongs to, not that list's type. `TodoListPolicy::view`/`update` was broadened so any active project member (not just the list's `owner_id`, which is null for a checklist) can add, toggle and remove its items — collaborative task work, unlike a personal to-do list.
- [x] Optional scheduled job generating each user's daily list (`oms:generate-daily-todo-lists`, `routes/console.php`, dailyAt 00:30 — after reconciliation and the progress snapshot, so the list it builds sees the day's corrected data). Not required for the feature to work (the My To-Dos page generates on demand regardless), but means the list already exists before the user ever opens the page.

## Phase 4 — Meetings and Minutes

- [x] `OMS\MeetingController` with scheduling and cancellation (FR-6.1) — route with `->except(['create', 'edit'])`; `show` is kept, same deep-linkable-workspace exception as the task detail page (ADR-013). `MeetingPolicy` mirrors `ProjectPolicy`'s visibility split: a meeting with no `project_id` is visible to the whole team; a project meeting follows that project's own membership rule. Managing a meeting (`update`/`cancel`/`delete`) is allowed for its organizer, a manager of its project, or a team admin — not "any attendee." Scheduling a meeting auto-adds the creator as an `organizer` attendee, already `accepted` (no self-RSVP needed for the person who just created it). Cancelling is a dedicated action (`PATCH .../cancel`, `MeetingStatus::Cancelled`) rather than a general `status` field on the edit form, mirroring how Task's board status is a dedicated `move` route, not part of its own-fields form.
- [x] `OMS\MeetingAttendeeController` for invitations, RSVP and attendance marking (FR-6.2) — invite-only fields (`user_id` *or* `guest_name`+`guest_email`, plus `role`) are accepted on create; a new attendee always starts `invited` server-side, never a caller-chosen value. RSVP and attendance are both just `attendance_status` transitions handled by the same `update`, which stamps `responded_at` the first time an RSVP value (`accepted`/`declined`/`tentative`) is reached and `joined_at` the first time `attended` is reached — no separate `respond`/`markAttendance` routes. A registered user vs. a guest is fixed at invite time and not editable afterward (remove and re-invite instead). `(meeting_id, user_id)` uniqueness is validated in the request, not just left to the DB constraint, so a duplicate invite is a clean 422 rather than a 500.
- [x] Agenda builder with ordering and task linking (FR-6.3). `meetings.agenda` (free-text, "Agenda notes" on the edit form) and the structured, ordered `meeting_agenda_items` table are both real, separate things in this schema (DESIGN.md) — this builds the latter. Managing the agenda reuses `MeetingPolicy::update` — the same organizer/project-manager/admin boundary as the meeting and its attendees, not a fourth permission tier. Task linking is offered only when the meeting has a `project_id` — a team-wide meeting has no single task list to link against, so `SaveMeetingAgendaItemRequest` rejects `task_id` outright rather than guessing which project's tasks to search. Mirrors Task's own split for board position vs. own-fields: a dedicated lightweight `move` route (position only) and `toggle` route (`is_discussed` only), separate from the general `update` (title/description/notes/duration/task/presenter) — reusing established idioms rather than inventing new ones. The reorder buttons genuinely swap both items' positions (two sequential requests), not just copy one position onto the other — see the MEMORY.md entry on why the single-sided version (the pattern Task/Module reordering already uses elsewhere in this app) can silently fail to reorder at all.
- [x] Minutes editor with a publish step stamping `minutes_published_at` (FR-6.4). `MeetingPolicy::recordMinutes` is deliberately broader than `canManage`: the attendee invited specifically with the `note_taker` role can record minutes too, even without rights to edit the meeting itself, its attendees or its agenda — matching what that role exists for. Publishing is idempotent: it stamps `minutes_published_at` only the first time, a second click is a no-op on the timestamp (but still re-stamps `recorded_by` to whoever clicked it, same as every save). Minutes stay editable after publishing — there's no "unpublish" step and no field-locking, since a published minutes doc still needing a typo fixed shouldn't require reversing the publish first. `meetings.recorded_by` updates on every save (not only on publish), tracking who most recently touched the minutes.
- [x] `GetOrCreateMeetingActionList` action creating a `meeting_actions` to-do list, lazily on first visit to the meeting workspace — same pattern as `GetOrCreateTaskChecklist` (FR-6.5). Reuses the existing `TodoItemController` routes verbatim; nothing new needed there since an item only cares which `TodoList` it belongs to, not that list's type. Scoping decision: `TodoListPolicy::view` was extended so *any* user who can see the meeting (`MeetingPolicy::view` — an attendee, or the same wide/project visibility the meeting itself grants) can add, toggle, promote and remove action items, not just the organizer/project-manager tier that manages the meeting's own fields — capturing and closing out action items is collaborative meeting work, same reasoning as why any active project member (not just a manager) can touch a task checklist.
- [x] Meeting timer writing a `time_logs` row against the meeting (FR-6.6). `ToggleMeetingTimer` is a small action with `start`/`stop`, reachable via two new routes (`POST/PATCH meetings/{meeting}/timer/start|stop`) authorized the same as viewing the meeting — any attendee can log their own time. A user may only have one running timer at a time, globally (`TimeLog::running()`), so starting a second one anywhere is rejected with a 422 rather than silently letting two entries overlap. Deliberately scoped narrow: this does **not** touch `meetings.status`/`started_at`/`ended_at` (the meeting's own lifecycle columns, still unset by anything in the app) — those track the meeting itself, not personal time logging, and FR-6.6 only asks for the latter. Whoever stops the timer is credited with the `time_logs` row; there's no notion of a single "the" meeting timer shared by all attendees, each attendee runs their own.
- [x] Minutes published notification to attendees. `App\Notifications\Meetings\MinutesPublished` (queued mail) is sent once, only from the timestamp-stamping branch of `publishMinutes` — a later idempotent re-publish never re-sends it. Registered attendees are notified via `$user->notify(...)`; guest attendees (no `user_id`) via `Notification::route('mail', $attendee->guest_email)->notify(...)`, the same on-demand pattern `TeamInvitationController` already uses.
- [x] Meeting list and calendar views — list only; a calendar view is not part of this step and stays open. `{current_team}/meetings`, filterable by status and type, plus a new "Meetings" sidebar link. Visibility in the list reuses the exact same rule as `MeetingPolicy::view`, applied as a query scope (team-wide meetings, or project meetings for projects the user is on, or every meeting for a team admin) rather than filtering the full set in PHP after loading it.

## Phase 6 — Availability and Time

- [x] `UserWorkScheduleController` for the weekly template, versioned by effective date (FR-8.1). Scoped to the acting user's own schedule only — no route-bound model, no policy class, same self-scoped reasoning as `MyDayController`; editing a *different* member's schedule is deliberately left to whoever picks up FR-8.8 (it's the same "a manager needs restricted visibility into someone else's schedule" question, already flagged there as needing an ADR, so it isn't re-solved ad hoc here). `SetUserWorkSchedule` writes a full week (all 7 `day_of_week` rows) as one version sharing an `effective_from`; a still-open earlier version is end-dated the day before, but resubmitting the *same* `effective_from` (correcting today's edit a second time) replaces that version in place rather than end-dating it a day before itself, which would otherwise collide with the `(user_id, day_of_week, effective_from)` unique constraint on re-insert. Cancelling sets `status = cancelled` rather than deleting the row (no soft-delete column exists) so a withdrawn request stays visible in the requester's own history. ## Phase 7 — Platform Administration and Access Control

Added 2026-09-22, per explicit user direction, after confirming four architectural forks with the user first (see below) since guessing wrong on any of them meant rebuilding auth/registration from scratch. This phase changes who is allowed to create a team and introduces a platform-level admin concept that doesn't exist anywhere in the app today — every existing role (`TeamRole::Owner/Admin/Member`) is scoped to one team, with no notion of a person who isn't a member of any team at all.

Confirmed with the user before starting:
- **Super admin is a separate auth guard**, not a flag on the existing `users` table — a distinct `admins` table/model/session, its own `/admin/login`, no sharing of Fortify's user-guard session. Isolation over reuse.
- **The existing self-service "Settings → Teams" flow loses only team *creation*.** A user can no longer create their own team, but switching between teams they already belong to and leaving a team stay exactly as they are today.
- **`/register` keeps working**, but a freshly registered user is not on any team. They land on a holding page until a super admin assigns them as a team leader, or an existing team leader invites them via the already-working invitation-link flow.
- **The "role permission module" is a real, database-backed, admin-manageable RBAC system** (`roles`/`permissions` tables, not enums) — but scoped to *this new process*: who can create teams, assign team leaders, and manage other admins and roles, inside the new `/admin` panel. It does **not** replace `TeamRole`/`TeamPermission`, which stay exactly as they are and keep powering every already-shipped OMS feature (dashboards, projects, tasks, capacity, approvals, all of Phases 1-6) completely unchanged. Rewriting that enum-based system application-wide was a real option but was rejected as disproportionate risk for what was asked — "a role permission module to manage this process," not "replace the authorization system this entire app already runs on." Worth a short ADR once built, since it's a genuine scope boundary someone could reasonably read differently.

### 7.2 Admin authentication

- [x] A small dedicated login/logout flow for the `admin` guard (`App\Http\Controllers\Admin\AuthController`) — not Fortify. Plain email + password, `Auth::guard('admin')->attempt()`, basic rate limiting (5 attempts/minute per email+IP, mirroring Fortify's own throttling without pulling in its machinery), `auth:admin` / `guest:admin` middleware.

- [x] Two real bugs found and fixed while live-verifying this in a browser, both pre-existing latent issues this phase was the first thing to ever reach:
  - **`HandleInertiaRequests::share()` crashed on every `/admin/*` request** with `Call to undefined method App\Models\Admin::toUserTeams()`. Cause: Laravel's `Authenticate` middleware calls `Auth::shouldUse($guard)` on success, which changes the *default* guard for the rest of the request — so `$request->user()` (no guard argument, called in the globally-shared `HandleInertiaRequests` middleware) started resolving to the `Admin` instance instead of `null`, and the middleware unconditionally called `User`-only team methods on whatever it got back. Fixed by checking `$user instanceof User` before building the `currentTeam`/`teams` shared props. This uncovered a second-order problem: because `$request->user()` can now genuinely return `App\Models\Admin|App\Models\User|null`, Larastan started (correctly) flagging every one of the ~29 existing controllers/requests/middleware that called bare `$request->user()`/`$this->user()` expecting only a `User` — fixed by making all of them explicit (`$request->user('web')`), which is the more honest statement of what each of those routes actually expects now that a second guard exists, not a workaround.
  - **Laravel's default guest/auth redirects assumed a single guard and broke for `admin`.** `RedirectIfAuthenticated`'s default (`Route::has('dashboard') ? route('dashboard') : ...`) doesn't know which guard triggered it, and `dashboard` is the *team-scoped* route name — calling it for an admin with no team context threw `Missing required parameter: current_team`. Fixing this took two attempts: registering `Authenticate::redirectUsing()`/`RedirectIfAuthenticated::redirectUsing()` from `AppServiceProvider::boot()` worked perfectly live in a browser but *silently failed under every PHPUnit test*, landing on `/login` instead of `/admin/login` — a genuine Laravel bootstrap-order trap (`ApplicationBuilder::withMiddleware()` registers its own default `redirectGuestsTo(route('login'))` inside the same `afterResolving(HttpKernel::class, ...)` hook that runs `bootstrap/app.php`'s callback, and that hook fires *after* provider boot in real HTTP requests but *before* it under PHPUnit's test bootstrap — so a provider-registered override wins in one context and silently loses in the other). Moved the registration into `bootstrap/app.php`'s own `withMiddleware()` closure using `$middleware->redirectTo(guests: ..., users: ...)`, the one place guaranteed to run after Laravel's default in both contexts — full writeup in `MEMORY.md`. Verified both the new admin flow and the entire existing regular-user login/dashboard flow live and under the full test suite afterward, with zero regressions.
